# 音频转弹唱谱

把一首混音成品歌变成**能直接照着弹唱**的谱：主旋律、逐字歌词、和弦、指法图、TAB、段落结构，附质量报告。

## 默认约定

- 输入是混音成品歌，不做多轨录音的分轨混音。人声用于旋律与歌词，伴奏用于和声。
- 默认难度 `elementary`，自动定调、自动算 capo。
- 全过程本地运行，用户音频不外传。
- 用户明确给出的调 / capo / 难度 / 曲段优先于自动推断。

## 执行步骤

### 1. 先自检

```bash
python scripts/doctor.py --json
```

读 JSON：

| 字段 | 含义 |
| --- | --- |
| `ready` | 能否运行 |
| `capabilities.separation.ok` | 能否分轨（决定旋律可信度） |
| `capabilities.lyrics.ok` | 能否识别歌词 |
| `degraded` | 缺哪些可选组件（`torch` / `demucs` / `faster_whisper`） |
| `paths.aitsm_root` | 解析到的项目根 |
| `advice` | 一句话结论 |

`ready: false` → 把 `locate_error.hint` 或 `missing_required` 原样告诉用户，**不要**继续硬跑。
`degraded` 非空 → 先说明质量会降多少（见下表），再问用户是否继续。不要静默降级。

| 缺失 | 实际后果 |
| --- | --- |
| `torch` / `demucs` | 无法分轨。旋律会锁到贝斯/伴奏上（音高基本不可用），和弦也会变差 |
| `faster_whisper` | 没有歌词，只有旋律与和弦；谱面歌词行留空 |

### 2. 确认输入

文件存在、格式可解码（mp3 / flac / wav / m4a / mp4 等）。时长决定耗时：

| 时长 | CPU 冷启动（首次，含分轨） | 分轨缓存命中 |
| --- | --- | --- |
| 4 分钟 | 约 9–10 分钟 | 约 4 分钟 |

> 实测基线来自本机 Windows 11 / Python 3.12.8 纯 CPU（**GPU 未启用**）：
> 229 秒的歌冷启动 539–618 秒，其中分轨 147–335 秒、歌词 151–157 秒（管线内）。
> 歌词占大头是因为默认用 whisper **medium**；`--whisper-model small` 能把歌词时间从约 2.5 分钟压到约 1 分钟，但 CER 会差约 0.10。
> 开 GPU 会快很多，但本机未验证。告诉用户「几分钟」，不要承诺「几秒」。

超过 8 分钟先提醒预计耗时。只想要一小段时用 `--start` / `--duration` 会更慢的说明不了——直接说明它不支持截取，建议用户先剪好文件。

### 3. 生成

```bash
python scripts/generate.py "<音频文件>" --out <输出目录>
```

常用参数：

```bash
--key G --capo 2          # 指定调与变调夹品
--difficulty beginner     # beginner / elementary / intermediate / advanced
--language zh             # 歌词语言；默认 auto
--device cpu              # auto / cuda / cpu
--whisper-model small     # 歌词模型降级（默认 medium；small 约快 2 倍、CER 高约 0.10）
--quality high            # 质量档：high 用微调分轨（约 4 倍慢），max 再加多次位移与 large-v3 歌词（1.5 小时以上）
--no-separation           # 跳过分轨（快，但旋律基本不可信）
--out <dir>               # 不给则自动选可写位置
```

**stdout 就是一个 JSON 对象**，直接读，不要解析日志（进度日志走 stderr）。
关键字段：

```jsonc
{
  "ok": true,
  "out_dir": "...",
  "summary": {
    "key": "D", "mode": "major", "capo": 0, "tempo": 92.28,
    "time_signature": [4, 4], "bars": 88, "sections": 5,
    "quality_overall": 0.652,
    "chord_events": 126, "melody_notes": 329, "lyric_notes": 302
  },
  "usable": true,                    // quality_overall >= 0.70
  "verdict": "good" | "fair" | "poor",
  "needs_review": [                  // 已按严重程度排序，high 在前
    {
      "severity": "high" | "medium" | "low",
      "code": "chords.bar_low_confidence",
      "what": "2 个小节的和弦置信度低于 0.55",
      "where": "第 32–33 小节（主歌 1）",
      "bars": [32, 33],
      "start_sec": 74.2, "end_sec": 79.1,
      "action": "在网页里点这些小节对照原曲听一遍，必要时重跑或人工改"
    }
  ],
  "needs_review_counts": { "high": 0, "medium": 3, "low": 5 },
  "files": { "score.json": "...", "score.musicxml": "...", "score.mid": "...", "report.md": "..." }
}
```

`ok: false` 时读 `error` / `hint` / `stderr_tail`，把它们转述给用户，**不要**自己编产物。

### 4. 读报告

`report.md` 是人类可读版，`needs_review` 已经在里面按严重程度分组。交付时按它的顺序讲。

## 交付时说什么

必须包含这四项：

1. **基本信息**：调性（原曲检测调）、capo、BPM、拍号、小节数、段落结构、难度
2. **文件路径**：`score.json`（网页）、`score.musicxml`（MuseScore / Guitar Pro）、`score.mid`
3. **真实限制**，精确到位置。示例：
   - 「第 32–33 小节和弦置信度 0.51，建议对照原曲确认」
   - 「歌词为自动识别，平均置信度 0.30，建议以原曲为准；02:14–02:48 那几行尤其需要校对」
   - 「42% 的旋律音符没匹配到歌词，那些位置留空——不是漏掉，是不编造」
4. **改编说明**（如有）：双吉他合并为单轨扫弦、原曲转调段落按统一调处理等

不要写「准确率 89%」。`confidence` 是**相对质量分**，措辞用「置信度 0.89」。
不要因为 `quality_overall` 低就不给结果——低质量 + 说清楚，比不给有用。

## 质量判读

完整规则见 [质量判读](references/quality.md)。至少记住：

| 指标 | 正常 | 需要提醒 | 视为失败 |
| --- | --- | --- | --- |
| `quality_overall` | ≥ 0.70 | 0.55–0.70 | < 0.55 |
| `stages.beats` | ≥ 0.75 | 0.55–0.75 | < 0.55（速度错→时值全错） |
| `stages.key` | ≥ 0.65 | 0.45–0.65 | < 0.45（调号错→和弦全偏） |
| `stages.chords` | ≥ 0.60 | 0.45–0.60 | < 0.45 |
| `stages.melody` | ≥ 0.60 | 0.40–0.60 | < 0.40 |
| `stages.lyrics` | ≥ 0.50 | 0.30–0.50 | < 0.30 |
| 段落数 | 5–12 | 3–4 或 13–16 | < 3 或 > 16 |
| 旋律音域 | MIDI 55–84 | 50–54 / 85–88 | 超出 48–90（八度错） |

`melody` 与 `lyrics` 只作参考，不与和弦/节拍直接比较。

## 可视化（可选）

```bash
python scripts/serve.py --score <输出目录>/score.json
```

它会打印一个本地 URL。这是**常驻进程**：要作为后台任务启动，只把 URL 告诉用户，不要让前台阻塞。
网页里可以移调（±6 半音）、改 capo（0–7 品）、播放跟随、A4 打印。

## 红线

1. **不伪造**：信号缺失就留空 + 告警。绝不猜音符、猜歌词填充。
2. **不隐藏降级**：任何引擎缺失、分轨失败、`lyrics.engine == "none"`，必须出现在交付说明里。
3. **不宣称准确率**：`confidence` 不是概率。
4. **不省略位置**：低置信度小节号、待校对歌词时间，必须给出具体位置。
5. **不越界承诺**：它做的是弹唱谱，不是乐队总谱，不是 MuseScore 工程，不是作曲。
6. 用户音频只在本地处理。

## 已知限制（面向用户如实转述）

- **歌词**：本机实测英文歌字符级 CER ≈ 0.49–0.54（medium 模型，跑完整管线后；同一配置三次运行差 0.05，因为分轨不是比特可复现）。会自动过滤 whisper 的复读与幻觉，但**不保证每句都对**，建议对照原曲校对。`--whisper-model small` 约 0.64，更快但明显更差。
- **和弦**：整体在调内、可行，但历史实测平均置信度约 0.58（54 个事件 / 88 小节）。失真吉他、大量七和弦的色彩和声会判得偏保守（宁给三和弦不给错和弦）。
- **关系大小调**（如 Bm vs D）音频上常难区分，默认按关系大调标注；用户知道原曲是小调时用 `--key` 指定。
- **速度/拍号中途变化**不支持（会告警，按主要速度记谱）。
- **多声部人声**（合唱、和声层）不支持，只取主旋律。
- **MusicXML** 通过官方 MusicXML 4.0 XSD 校验，并已在 **MuseScore Studio 4.7.5** 实机打开核对（双谱表/和弦/逐字歌词/段落/速度标记均正确）；再用 `MuseScore4.exe -o out.pdf score.musicxml`（不加 `-f`）严格导入也是 exit 0。若用户用其它软件打不开，仍请收下具体报错，不要声称那款软件已验证。
- **GPU 未启用**：全流程 CPU，4 分钟歌约 9–10 分钟（冷启动，medium 歌词模型）。

## 中文歌特别注意

中文（普通话）歌会额外走三步清洗，**不要把这些当成"已经完美"**：

1. **署名行幻觉**：整行「作词: xxx」「詞曲: xxx」会被丢弃——那通常是静音段 whisper 编的，不是真歌词。
2. **单字碎行**：「去」「息」这类换气切出来的 1 字行会并入相邻行，谱面上不再一个字占一行。
3. **繁简统一**：歌词会转成简体（`zhconv`；用户要繁体时设 `AITSM_KEEP_TRADITIONAL=1`）。

向用户转述中文歌质量时：

- **不要用英文歌的 CER 承诺准确率**。英文按字符级 CER 报（0.49–0.54）；中文按
  `lev_cer / recall / precision` 三元组报（本机实测 0.669 / 0.835 / 0.606），并说明"recall 高代表漏词少，precision 低不代表乱编，多数是重复副歌与逐字误识"。
- **不要承诺逐行时间对得上 LRC**：用户的 .lrc 常与音频不是同一编曲版本（本机实测首行标 2.08s，
  但人声 14.8s 才起，偏移还会漂移）。做的是音频对齐，不是 LRC 对齐。
- 真正的错误是**逐字误识**（如「神奇」→「闪起」、「异己」→「一记」），不是繁简问题；
  让用户用网页编辑器直接改词／改和弦比反复重跑更有效。
