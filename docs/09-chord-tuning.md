# 和弦识别调优：两处改动、一组对照实验、一个被数据否定的想法

> 一句话结论：**beat-synchronous 特征融合（中值聚合 + 谱归一化）有效，已设为默认；
> 重复一致性第二遍解码看着聪明，实测是负收益，保留代码但默认关闭。**

## 1. 为什么动这块

`score.json` 的 `quality.stages.chords` 长期卡在 0.57–0.58，`quality.overall` 被它和
歌词自评一起拖到 0.67 左右。`--quality high`（更贵的分轨模型 + large-v3 歌词）实测
只把和弦置信度抬高 1.2%（详见 [docs/08-quality-tiers.md](08-quality-tiers.md)），
说明**瓶颈不在模型规格，在识别器本身的特征层**。

## 2. 改动一：beat-synchronous 特征融合（默认开启）

原实现把每个和弦槽位内的 chroma 直接取**均值**。两个已知偏差随之而来：

1. **攻击瞬态污染**：鼓点、拨弦起音的那一两帧 chroma 是宽带分布，均值会被拉平，
   非和弦音的底噪被抬高，模板匹配的相对优势变小。
2. **响度偏差**：均值是能量加权，谁的音量大谁占主导。贝斯/底鼓一响，低频音级就通吃，
   三和弦容易被判成 `Cadd9` / `Cmaj7` / `Cmaj7/D` 这类「多出一个音」的和弦。

改法是两路特征各自归一化后融合（`_slot_matrix_fused()`，权重 `_FUSION_WEIGHTS = (0.62, 0.38)`）：

- **中值路（0.62）**：槽位内逐音级取中位数，抗离群帧。
- **谱归一化路（0.38）**：每帧先按自身能量归一化再取均值，抗响度偏差。

两路都做 L1 归一化后加权，最后仍沿用 3 点时间平滑（`_smooth_matrix`）。

顺手还试了一个微调：**槽位两端各裁掉 15%/30% 帧再聚合**（想法是「和弦在槽位边界换，
边界帧是两个和弦的混合」）。实测反而更差（下表 `fusion+trim15`/`fusion+trim30`），
因为槽位本来就短（4/4 是半小节 ≈ 1.3 s ≈ 56 帧听起来够，但扣除重叠与平滑后有效帧不多），
裁完中值不稳定。结论：`_SLOT_TRIM = 0.0`，代码保留但默认不裁。

## 3. 改动二：重复一致性第二遍解码（默认关闭）

想法：一首歌副歌唱三遍，其中一遍信号被衰减/加花搞糊。第一遍解码后，**相似槽位**
（`_repetition_weights()` 算槽位级自相似矩阵，阈值 0.93、每槽最多 24 个邻居、
排除 ±3 个相邻槽位）已经给出可信答案，第二遍把这份一致性证据加成到候选分上
（`_apply_repetition_prior()`，幅度 0.045），再解一遍 Viterbi。

这个想法在合成曲上「看起来很好」：末段做旧的那遍副歌仍然 100% 正确——但那是因为
合成曲本来就不难，和这个机制无关。到真歌上就露馅了。

## 4. 对照实验：没有和弦标注时怎么判断好坏

真歌没有和弦标注，所以用三个**客观代理指标**（`work/eval-robust.py`）：

- **调内三和弦干净率**：输出的和弦里有几成是「调内 + 三和弦」。流行歌 95% 以上应是三和弦，
  出现 `sus2`/`m7b5`/斜杠越多，说明识别器在用复杂和弦解释噪声。
- **跨分轨一致率**：同一首歌用两个分轨模型（`htdemucs` / `htdemucs_ft`）的伴奏各识别一次，
  两次结果在 0.1 s 网格上逐点比对的一致率。识别器越稳，这个数越高。
- **事件数 / 平均置信度**：和上面一起看，防止「靠少换和弦把一致率刷上去」。

合成曲有 ground truth（`work/eval-chords.py`），但**四首全部 100%**、四种配置完全一样，
说明合成信号对这套方法太容易，只能用来防回归，不能用来选参数。

### 实测数据（229 s 真歌，两个分轨模型）

`accept-v2`（`htdemucs` 分轨，素材与 beats/key 完全相同，只换识别配置）：

| 配置 | 事件数 | 平均置信度 | 调内三和弦 | 复杂和弦 |
| --- | --- | --- | --- | --- |
| baseline（旧：均值聚合） | 49 | 0.5891 | 93.9% | 6.1% |
| **fusion（默认，trim=0）** | 51 | **0.5928** | **98.0%** | **2.0%** |
| fusion+trim15 | 56 | 0.5903 | 96.4% | 3.6% |
| fusion+trim30 | 63 | 0.5891 | 95.2% | 4.8% |
| repetition（fusion 关闭） | 48 | 0.5922 | 95.8% | 4.2% |

`accept-max`（`htdemucs_ft` 分轨）：

| 配置 | 事件数 | 平均置信度 | 调内三和弦 | 复杂和弦 |
| --- | --- | --- | --- | --- |
| baseline | 52 | 0.5811 | 96.2% | 3.8% |
| **fusion（默认，trim=0）** | 65 | 0.5721 | **96.9%** | 3.1% |
| fusion+trim15 | 65 | 0.5716 | 95.4% | 4.6% |
| repetition | 60 | 0.5753 | 96.7% | 3.3% |

跨分轨一致率（`htdemucs` 识别结果 vs `htdemucs_ft` 识别结果，同配置）：

| 配置 | 一致率 |
| --- | --- |
| baseline | 55.2% |
| **fusion** | **57.4%** |
| repetition | 47.7% |

### 结论

- **fusion 小胜且方向一致**：干净率 93.9%→98.0%（v2）与 96.2%→96.9%（max），
  置信度在 v2 上 +0.004，跨分轨一致率 +2.2 个点，事件数只多 2 个。它是
  「同样的证据，打分更干净」，没有引入新的先验，所以敢默认开。
  在 `htdemucs_ft` 分轨上事件数从 52 涨到 65 但置信度略降（0.5811→0.5721），
  这是「分轨更干净 → 半小节换和弦看得见 → 事件变多、平均时长变短」的连锁反应，
  不是精度退化（干净率同时从 96.2% 升到 96.9%）。
- **repetition 是负收益**：跨分轨一致率掉到 47.7%（−7.5 点），也就是说它把
  「两个分轨模型本来能达成一致的地方」改坏了；干净率虽略升，但事件数在两组实验里
  乱跳（48/60），说明它在跟噪声对赌。

## 5. 为什么 repetition 会失败（值得记下来）

三个具体原因，都不是「参数没调好」：

1. **相似度本身就不可靠**。做旧/加花的段落，chroma 与它「应该像」的槽位相似度会一起下降，
   恰好在最需要证据的地方拿不到证据。
2. **自训练会放大第一遍的错**。第一遍在模糊段落解错时，错误答案也会成为邻居的「投票」，
   第二遍把错误固化下来。真歌里那 172 个被改动的槽位，多数属于这一类。
3. **它奖励「少换和弦」**。一致性证据天然偏好「和邻居一样」，而音乐里恰恰存在
   「同样的伴奏换一个和弦」的写法。排除 ±3 相邻槽位只能缓解，不能消除。

教训一句话：**跨段证据要想有用，先得能证明「不同段落在声学上真的对应」，
而不是「长得有点像」。** 这和段落检测难是同一个根问题。

## 6. 怎么复现

```bash
# 合成曲：有 ground truth，用来防回归（四首应全部 100%）
python -m aitsm.testsupport.synth_song --out work/synth-hard --profile busy --profile waltz --profile rock
python work/eval-chords.py

# 真歌稳健性：干净率 / 跨分轨一致率 / 事件数
python work/eval-robust.py

# 开/关这两个机制（默认 fusion 开、repetition 关）
AITSM_CHORD_FUSION=0 python -m aitsm.cli generate song.flac --out work/no-fusion
AITSM_CHORD_REPETITION=1 python -m aitsm.cli generate song.flac --out work/with-repetition
```

`manifest.json` 的 `stages.analysis` 里 chords 阶段的 `extra` 会记录
`feature_fusion` / `repetition_touched_slots` / `slots`，和弦事件的 `source`
字段会写成 `chroma-template+bass-stem+viterbi`（开启重复一致性时追加 `+repetition(N)`），
所以「这份谱是哪个配置产出的」永远可追溯。

## 7. 还能往哪儿走

按预期收益排序：

1. **频谱特征而非纯 chroma**：chroma 把八度折叠掉了，也丢掉了音色；用 log-mel +
   小 CNN 或 NMF-based 模板能在「同一和弦不同配器」上明显更稳。这是真正的大头。
2. **段落内和弦集合约束**：先估每段的和弦候选集合（比如只允许 4–6 个和弦），
   再在段内解码。当前段落检测在真歌上还不够稳（见 docs/07 第 5 节），所以先得
   把段落搞定，否则约束会跟着错。
3. **手改闭环**：网页编辑器已经能改和弦并回写 `score.json`，人工修正的性价比
   仍然高于继续堆模型。
